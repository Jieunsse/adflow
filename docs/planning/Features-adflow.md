# AdFlow 기능명세 (1차 출시)

작성일: 2026-11-11 · 상태: 초안 (확정 전) · 범위: 기획서 6.2의 1차 기능 15개

기준 문서: `PRD-adflow.md`, `Policy-adflow.md`, `TestScenarios-adflow.md`, `docs/company/01`~`07`

## 0. 이 문서를 읽는 법

### 0.1 이 문서가 정하는 것

- 이 문서는 1차 기능을 "어떤 화면에서, 누가, 어떤 순서로 쓰는지"로 옮깁니다.
- 규칙(글자 수, 권한, 판정 조건 같은 것)은 정책서에 있습니다. 이 문서는 규칙을 다시 쓰지 않고 정책서 절 번호를 적습니다. 둘이 다르면 정책서를 따릅니다.
- 화면 문구는 해요체로 씁니다. 문구는 초안이고, 시안 단계에서 `.document/UX-WRITING.md`에 맞춰 다듬습니다.
- 피그마 Features 페이지와 Main Design 시안은 이 문서를 기준으로 만듭니다.

### 0.2 기능 하나의 구성

| 칸 | 내용 |
|---|---|
| 목적 | 이 기능이 왜 있는지 한두 문장 |
| 쓰는 사람 | 역할 (정책서 5.1) |
| 흐름 | 사용자가 하는 일의 순서 |
| 화면 | 화면마다 주소, 구성, 동작, 상태별 모습, 주요 문구 |
| 관련 문서 | 정책서 절, 시험 시나리오 번호 |
| 지금 코드 | 이미 있는 화면과 파일. 경로는 `apps/web/` 기준 |

### 0.3 상태별 모습

모든 화면은 아래 네 가지 상태를 그립니다. 기능별로 특별한 것만 따로 적습니다.

| 상태 | 기본 모습 |
|---|---|
| 불러오는 중 | 화면 뼈대만 회색으로 보여 줍니다 |
| 비어 있음 | 왜 비었는지와 다음 할 일 버튼 하나 |
| 오류 | 무엇이 안 됐는지, 왜인지, 다음에 무엇을 하면 되는지 (정책서 0.4) |
| 권한 없음 | 화면에 들어오지 못하게 막고 대시보드로 보냅니다. 버튼 단위는 숨깁니다. 서버도 거절합니다 (정책서 5.2) |

## 기능 1. 실험 만들기

- **목적:** 가설 하나와 바꾸는 요소 하나를 정해 실험을 시작합니다. 이긴 이유를 알 수 있게 하는 출발점입니다.
- **쓰는 사람:** 담당 직원 (팀원·게재), 콘텐츠 마케터 (팀원·검토, 요청까지만)
- **관련 문서:** 정책서 8, 9, 11.4절 · 시나리오 TS-01, TS-12
- **지금 코드:** `/ab-tests/new` → `src/widgets/tournament-setup/index.tsx` (방식 선택 → A/B 설계 → 게재 조건). 가설과 "바꾸는 요소 하나" 검사는 없습니다

**흐름**
1. 실험 화면이나 오늘의 결정에서 "실험 만들기"를 누릅니다.
2. 이번 달 승인된 월간 계획 안의 실험 묶음을 고릅니다. 새 묶음이면 목표와 상품을 고릅니다.
3. AI가 가설 초안 3개를 보여 줍니다. 하나를 고르거나 고치거나 직접 씁니다.
4. 바꾸는 요소를 하나 고릅니다.
5. 하루 예산과 기간을 확인합니다.
6. 저장하면 "소재 준비 중"이 되고 소재 만들기(기능 2)로 넘어갑니다.

**화면 1-1. 실험 만들기** (`/ab-tests/new`)

| 단계 | 구성 | 동작과 규칙 |
|---|---|---|
| ① 실험 묶음 | 이번 달 계획의 묶음 목록(목표, 상품, 남은 예산). "새 묶음" 버튼 | 계획에 없는 상품이나 목표는 고를 수 없고 "월간 계획을 고쳐 고객에게 다시 승인받아 주세요"로 안내합니다 (정책서 11.4) |
| ② 가설 | AI 초안 3개 카드, 직접 쓰기 칸. 카드마다 근거(어느 기록, 과거 기록)를 작게 표시 | 비워 두면 다음으로 갈 수 없습니다. 문구: "무엇을 확인하려는지 한 줄만 적어 주세요." |
| ③ 바꾸는 요소 | 헤드라인, 첫 문장, 이미지, 행동 유도 버튼 (1차는 형식과 쇼츠 없음) | 하나만 고를 수 있습니다. 이미 "효과 없음"으로 끝난 값은 "이미 시험했어요" 표시와 함께 흐리게 둡니다 (정책서 9.2) |
| ④ 예산과 기간 | 하루 예산(3만, 5만, 10만, 20만, 직접 입력), 기간(기본 7일), 예상 총비용, 이번 달 상한까지 남은 금액 | 예상 총비용이 남은 금액을 넘으면 저장은 되지만 게재 요청 때 막힌다고 미리 알려 줍니다 |
| ⑤ 확인 | 고른 내용 요약 | "저장하고 소재 만들기" |

- **"기존 광고로 시작" 모드:** 지금 코드의 "기존 광고로 시작"은 기준 소재를 고르는 방법으로 남깁니다. ① 단계의 새 묶음에서만 보입니다.
- **오늘의 결정에서 들어오면** ②, ③이 채워진 채로 열립니다 (정책서 15절).

## 기능 2. 소재 만들기

- **목적:** 기준 소재에서 바꾸는 요소 하나만 다른 도전 소재를 만듭니다.
- **쓰는 사람:** 담당 직원, 콘텐츠 마케터
- **관련 문서:** 정책서 6, 7, 10.1~10.3, 14.4절 · 시나리오 TS-03
- **지금 코드:** `/create` (`BriefStep` → `CompareStep` / `ImageConceptStep` / `RefineStep` → `LaunchStep`), 실험용은 `src/widgets/tournament-setup/ChallengerImageGen.tsx`, 도전 소재 카피는 `app/api/internal/creative/challenger/route.ts`

**흐름**
1. 실험에서 "소재 만들기"를 누르면 기준 소재가 왼쪽, 도전 소재가 오른쪽에 나란히 열립니다.
2. 바꾸는 요소 칸만 편집할 수 있고, 나머지는 기준 소재와 같게 잠깁니다.
3. AI 후보를 고르거나 다듬기 버튼(더 짧게, 더 부드럽게, 숫자 강조, 행동 유도 더하기)을 씁니다.
4. 브랜드 규칙 검사 결과를 확인하고 "검수 요청"을 누릅니다. 콘텐츠 마케터가 검수합니다.

**화면 2-1. 소재 나란히 보기** (`/ab-tests/[id]/creative`, 새로)

| 영역 | 구성 | 동작과 규칙 |
|---|---|---|
| 위 | 가설, 바꾸는 요소, 쓴 브랜드 지식(접힘) | 지식을 썼으면 "지식을 쓴 소재" 표시 (정책서 10.1) |
| 가운데 | 기준 소재 미리보기와 도전 소재 미리보기. 피드 1:1과 4:5 전환 | 바꾸는 요소만 색으로 강조합니다 |
| 오른쪽 | 바꾸는 요소 편집 칸, AI 후보 3개, 다듬기 버튼, 남은 글자 수 | 글자 수를 넘으면 저장할 수 없습니다 (정책서 10.2) |
| 아래 | 브랜드 규칙 검사 결과 (막기 몇 개, 경고 몇 개). 만든 AI 이름 | 막기가 하나라도 있으면 "검수 요청"이 눌리지 않습니다 |

- 이미지를 바꾸는 실험이면 오른쪽에 이미지 생성 칸(최대 4장, 참고 이미지 최대 6장)이 열립니다. 고객이 준 제품 사진은 브랜드 참고 자료에서 고릅니다.
- 브랜드 규칙을 어기면 어긴 부분에 밑줄을 긋고, 규칙 이름과 고치는 방법을 보여 줍니다. 예: "헤드라인이 35자예요. 30자 이하로 줄여 주세요."

**화면 2-2. 검수** (화면 2-1과 같은 화면, 검수 모드)

| 구성 | 동작 |
|---|---|
| 콘텐츠 마케터에게 "검수할 소재" 목록이 승인 화면에 따로 보입니다 | 고치고 "검수 완료"를 누르면 담당 직원에게 알림이 갑니다 |
| 고친 부분은 "사람이 고침"으로 기록됩니다 (정책서 10.1) | 검수 완료 후 담당 직원이 게재 요청을 합니다 (기능 7) |

- **검수 단계를 따로 두는 이유 (확정).** 조직 문서 2절에서 소재 검수를 콘텐츠 마케터 일로 정했습니다. 실험 상태에 "검수 중"을 더했습니다 (정책서 9.5, 9.6).
- **콘텐츠 마케터를 뽑기 전 (확정).** 담당 직원이 자기 소재를 "검수 완료"로 넘길 수 있습니다. 누가 검수했는지는 기록됩니다. 콘텐츠 마케터가 들어오면 팀장이 설정에서 "본인 검수 허용"을 끕니다.

## 기능 3. 판정

- **목적:** 데이터가 충분할 때만 승패를 정하고, 모자라면 무엇이 모자란지 보여 줍니다.
- **쓰는 사람:** 시스템이 판정하고, 담당 직원이 결과를 봅니다
- **관련 문서:** 정책서 12, 13절 · 시나리오 TS-05
- **지금 코드:** `/ab-tests/[id]` (`DecisionBanner`, `buildRoundReport`), 판정 규칙은 `src/entities/ab-test/tournament/engine.ts`와 `apps/api/.../tournament/engine/TourEngine.java`. 최소 노출 수 검사가 없습니다. 판정 뒤 다음 실험을 자동으로 게재합니다 (`TournamentAdvanceService.autoAdvance`)

**화면 3-1. 실험 상세** (`/ab-tests/[id]`)

| 상태 | 위쪽 띠 | 본문 |
|---|---|---|
| 진행 중 | "데이터 모으는 중 · 판정까지 노출 620회 남았어요" | 소재별 노출, 클릭, 클릭률, 쓴 금액, 마지막으로 가져온 시각. 이기고 있는 쪽은 보여 주지 않습니다 (정책서 12절) |
| 판정 완료 | "도전 소재가 이겼어요" / "기준 소재가 이겼어요" / "차이가 없었어요" | 두 소재 지표, 차이(%), 신뢰도, 구매 전환(참고). "배운 것 확인하기" 버튼 |
| 판정 불가 | "판정하지 못했어요 · 노출이 620회 모자라요" | 제안 두 개: "기간 3일 늘리기", "하루 예산 4만 원으로 늘리기". 둘 다 승인을 거칩니다 |
| 멈춤 | "멈췄어요 · 이유" | 이유별 다음 할 일 (기능 13) |

- **다음 실험:** 판정이 끝나면 다음 도전 소재 초안을 미리 만들어 두고 "다음 실험 준비됐어요"를 오늘의 결정에 올립니다. 게재는 승인을 거칩니다 (정책서 11.3). 지금 코드의 자동 게재는 끕니다.
- 실험 묶음 전체 흐름(지금 코드의 여정 보기)은 화면 위쪽에 그대로 둡니다.

## 기능 7. 게재 요청과 승인 (안전장치)

- **목적:** 사람이 승인해야만 Meta에 올라가게 합니다. 게재 직전에 브랜드 규칙과 예산 상한을 다시 검사합니다.
- **쓰는 사람:** 요청은 직원 누구나, 승인은 그 브랜드의 담당 직원과 팀장
- **관련 문서:** 정책서 7.1, 11.1~11.4절 · 시나리오 TS-03, TS-04, TS-12, TS-13
- **지금 코드:** `/approvals`는 Meta 검토 상태 목록입니다. 내부 승인 단계가 없고, 승인 역할은 가짜 데이터(`lib/mock-members.ts`)에만 있습니다

**흐름**
1. 소재가 검수를 마치면 담당 직원이 "게재 요청"을 누릅니다. 게재 전 검사 12가지를 순서대로 돌립니다 (정책서 11.1).
2. 통과하면 "승인 대기"가 되고, 승인할 수 있는 사람에게 알림이 갑니다.
3. 승인 화면에서 내용을 확인하고 승인하거나 이유를 적어 반려합니다.
4. 승인하면 Meta에 꺼진 상태로 만들고, 모두 만들어지면 켭니다.

**화면 7-1. 승인** (`/approvals`)

| 탭 | 내용 |
|---|---|
| 승인할 것 | 내가 승인할 수 있는 요청. 브랜드, 실험, 요청한 사람, 요청 시각, 예상 총비용 |
| 검수할 것 | 콘텐츠 마케터에게만 보입니다 (기능 2) |
| 내가 요청한 것 | 상태(승인 대기, 반려, 승인됨) |
| Meta 검토 | 지금 화면의 내용 (검토 중, 이슈) |

**화면 7-2. 승인 상세** (오른쪽 패널)

| 구성 | 동작과 규칙 |
|---|---|
| 두 소재, 바꾸는 요소, 가설 | |
| 하루 예산, 기간, 예상 총비용 (승인 버튼 바로 위) | 정책서 11.2 |
| 이번 달 상한, 이미 쓴 금액, 승인하면 남는 금액 | 상한을 넘으면 승인 버튼이 눌리지 않습니다. 문구: "이번 달 예산 상한을 넘어요. 고객에게 상한을 늘려 달라고 요청해 주세요." |
| 브랜드 규칙 검사 결과 | |
| 버튼: 승인 / 반려 (10자 이상 이유) | 담당 직원이 아니면 버튼이 없습니다 |

**게재 요청 전 검사에서 걸렸을 때:** 걸린 첫 번째 항목 하나만 문구와 바로가기 버튼으로 보여 줍니다. 예: "광고 계정과 페이지가 연결되지 않았어요. 설정에서 연결해 주세요." [계정 연결로 가기]

## 기능 9. Meta 지난 광고 가져오기

- **목적:** 첫날부터 시작할 실험 후보를 만들고, 무료 진단서의 재료로 씁니다.
- **쓰는 사람:** 담당 직원, 팀장
- **관련 문서:** 정책서 14.3, 19.1절 · 시나리오 TS-10 · 영업 문서 5절
- **지금 코드:** 없음. 가장 가까운 것은 실험 만들기의 "기존 광고로 시작"에서 캠페인 하나를 고르는 것입니다

**흐름**
1. 브랜드에 광고 계정을 처음 연결하면 자동으로 시작합니다 (기능 10).
2. 진행 상황을 보여 주고, 끝나면 "과거 기록 (참고)" 탭에 쌓습니다.
3. 과거 기록에서 첫 실험 가설 후보를 3개까지 만들어 오늘의 결정에 올립니다.

**화면 9-1. 과거 기록** (`/learnings`의 "과거 기록 (참고)" 탭)

| 구성 | 동작과 규칙 |
|---|---|
| 위: "최근 12개월 광고 84개를 가져왔어요 · 2026. 11. 11." 과 "다시 가져오기" | 다시 가져오기는 사람이 누를 때만 합니다 |
| 광고 카드: 미리보기, 기간, 쓴 금액, 클릭률. "참고" 띠 | 브랜드 지식이 되지 않는다는 안내를 탭 위에 한 줄 둡니다 |
| 가설 후보: "이 광고들을 보면 ○○을 시험해 볼 만해요" | 누르면 실험 만들기가 채워진 채로 열립니다 |
| 가져오는 중 | 진행 막대와 "지난 광고를 불러오는 중이에요" |

**무료 진단 (영업):** 계약 전 고객사도 같은 기능을 씁니다. 고객사 상세(기능 14)에서 "진단용으로 가져오기"를 누르면 같은 과거 기록 화면이 진단 모드로 열리고, 1차에서는 직원이 이 화면을 보고 진단서를 직접 씁니다.

## 기능 10. 여러 브랜드 관리

- **목적:** 회사 워크스페이스 하나에서 대행 고객의 브랜드를 여러 개 운영합니다.
- **쓰는 사람:** 팀장이 만들고 담당을 정합니다. 직원은 바꿔 가며 씁니다
- **관련 문서:** 정책서 1, 2, 4.0, 5.1, 6.1절 · 시나리오 TS-13
- **지금 코드:** 브랜드 프로필은 여러 개 만들 수 있습니다 (`src/features/brand-profile/model/brandProfileStore.ts`). 워크스페이스가 없고 모든 데이터가 로그인한 사람 이메일에 묶여 있습니다 (`apps/api/.../store/OwnerScoped.java`). 광고 계정은 사람마다 1개입니다 (`MetaConnection.java`)

**흐름**
1. 고객사를 "계약"으로 바꾸면 같은 이름의 브랜드가 만들어집니다 (기능 14).
2. 팀장이 담당 직원을 정합니다.
3. 담당 직원이 파트너 공유로 받은 광고 계정과 페이지 중에서 이 브랜드의 것을 고릅니다.
4. 브랜드 프로필과 브랜드 규칙을 채웁니다 (운영 문서 2절의 시작 준비).

**화면 10-1. 브랜드 목록** (`/brand-profile`)

| 구성 | 동작 |
|---|---|
| 브랜드 카드: 이름, 담당 직원, 계약 상태, 시작 준비 진행(광고 계정, 프로필, 규칙, 첫 계획), 진행 중 실험 수 | 시작 준비가 안 끝난 항목은 체크 안 된 상태로 보입니다 |
| 거르기: 내 담당, 전체, 종료됨 | |

**화면 10-2. 브랜드 상세** (`/brand-profile/[id]`)

| 탭 | 내용 |
|---|---|
| 정보 | 지금 화면의 정체성, 고객, 제품, 근거 자료 (정책서 6.1) |
| 규칙 | 브랜드 규칙 (정책서 7절). 팀장만 고칩니다 |
| 연결 | 광고 계정, 페이지, 픽셀. "파트너 공유 받은 계정에서 고르기" |
| 담당 | 담당 직원 (팀장만 바꿈), 고객 계정 목록과 초대 (기능 11) |

**화면 10-3. 광고 계정 고르기** (연결 탭)

| 상태 | 모습 |
|---|---|
| 공유받은 계정 있음 | 아직 다른 브랜드에 연결되지 않은 광고 계정과 페이지 목록 |
| 없음 | "아직 공유받은 광고 계정이 없어요. 고객에게 파트너 공유를 요청해 주세요." 와 고객에게 보낼 안내 링크 복사 |
| 목록을 읽지 못함 | "공유받은 계정 목록을 불러오지 못했어요. 광고 계정 번호를 직접 넣어 주세요." 와 번호 입력 칸. 저장하기 전에 우리 비즈니스가 그 계정에 접근할 수 있는지 확인합니다 |
| 직접 입력한 번호에 접근할 수 없음 | "이 광고 계정에 접근할 수 없어요. 고객이 파트너 공유를 마쳤는지 확인해 주세요." 저장하지 않습니다 |
| 다른 브랜드에 이미 연결됨 | 고를 수 없고 어느 브랜드에 연결됐는지 보여 줍니다 |

- **목록과 직접 입력을 함께 두는 이유 (확정).** Meta 비즈니스 API로 공유받은 계정 목록을 읽을 수 있는지와 필요한 권한은 아직 확인하지 않았습니다 (19절). 목록을 못 읽어도 대행을 시작할 수 있게 합니다.

## 기능 11. 고객 역할과 고객 화면

- **목적:** 대행 고객이 자기 브랜드의 결과를 보고 월간 계획을 승인합니다.
- **쓰는 사람:** 고객 (고객사마다 최대 3명)
- **관련 문서:** 정책서 2, 5.1, 5.2, 17절 · 시나리오 TS-14
- **지금 코드:** 없음. 구성원 화면(`/members`)은 가짜 데이터입니다

**흐름**
1. 담당 직원이 브랜드 상세 › 담당 탭에서 고객 이메일로 초대합니다.
2. 고객이 초대 링크를 열고 로그인 방법을 고릅니다. 이메일 가입, 페이스북, 구글, 카카오 중 하나입니다 (정책서 3.1).
3. 로그인한 계정의 이메일이 초대한 이메일과 같으면 연결됩니다.
4. 고객은 `/portal`만 볼 수 있습니다.

**화면 11-0. 초대 수락과 로그인** (`/invite/[token]`)

| 영역 | 구성 | 동작과 규칙 |
|---|---|---|
| 위 | "○○ 브랜드의 광고 결과를 함께 보도록 초대받았어요", 초대한 담당자 이름 | 링크는 7일 동안 한 번만 쓸 수 있습니다 (정책서 5.3) |
| 로그인 버튼 | 카카오로 계속하기, 구글로 계속하기, 페이스북으로 계속하기, 이메일로 가입하기 | 순서는 시안에서 정합니다 |
| 이메일 가입 | 이메일(초대 이메일이 미리 채워지고 바꿀 수 없음), 비밀번호, 비밀번호 확인, 약관 동의 | 가입하면 인증 메일을 보내고, 인증해야 들어갑니다 |
| 이메일이 다름 | "초대받은 이메일(a***@brand.com)과 다른 계정이에요. 초대받은 이메일로 로그인하거나, 담당자에게 초대를 다시 요청해 주세요." | 연결하지 않습니다 |
| 링크 만료 | "초대 링크가 만료됐어요. 담당자에게 다시 요청해 주세요." | |

**화면 11-0-1. 고객 로그인** (`/login`의 고객 탭)

| 구성 | 동작 |
|---|---|
| 카카오, 구글, 페이스북, 이메일 로그인 | 처음 가입한 방법이 아니어도 이메일이 같으면 같은 계정으로 들어갑니다 |
| 이메일 로그인: 이메일, 비밀번호, "비밀번호를 잊었어요" | 실패가 5번이면 15분 동안 막습니다 (정책서 3.1) |
| 설정 › 로그인 방법 (`/portal/settings`) | 다른 로그인 방법을 더 연결하거나 끊습니다. 마지막 하나는 끊을 수 없습니다 |

**화면 11-1. 이번 달** (`/portal`)

| 영역 | 구성 |
|---|---|
| 맨 위 | 승인할 것이 있으면 "이번 달 계획을 확인해 주세요" 카드 (기능 12) |
| 요약 | 이번 달 쓴 광고비 / 상한, 진행 중 실험 수, 이번 달 확정된 배운 것 수 |
| 최근 배운 것 3개 | 카드, 누르면 `/portal/learnings` |
| 담당자 | 담당 직원 이름, 카카오톡 채널로 문의하기 |

**화면 11-2. 진행 중 실험** (`/portal/experiments`)

| 구성 | 규칙 |
|---|---|
| 실험 목록: 가설, 바꾸는 요소, 시작일, 판정까지 남은 정도 | 이기고 있는 쪽은 보여 주지 않습니다 (정책서 5.1) |
| 누르면 두 소재 미리보기 | 편집 버튼 없음 |

- 고객 역할이 `/portal` 밖 주소를 열면 `/portal`로 보냅니다. 서버도 거절합니다.

## 기능 12. 월간 계획과 총예산 상한 승인

- **목적:** 고객이 한 달에 한 번 계획과 예산 상한을 승인하고, 그 안에서는 직원이 게재를 승인합니다.
- **쓰는 사람:** 담당 직원이 만들고, 고객이 승인합니다
- **관련 문서:** 정책서 11.4, 12.1, 17절 · 운영 문서 3.1 · 시나리오 TS-12
- **지금 코드:** 없음

**흐름**
1. 매월 마지막 주에 담당 직원이 다음 달 계획을 만듭니다. 지난달 배운 것과 다음 실험 제안이 초안으로 채워집니다.
2. "고객에게 승인 요청"을 누르면 고객에게 알림이 갑니다. 담당 직원은 카카오톡 채널로 링크도 보냅니다.
3. 고객이 승인하거나 이유를 적고 반려합니다.
4. 월 중간에 상한을 늘리거나 계획을 바꾸려면 고쳐서 다시 승인받습니다.

**화면 12-1. 월간 계획 목록** (`/plans`)

| 구성 | 동작 |
|---|---|
| 브랜드별 이번 달, 다음 달 계획 상태: 작성 중, 승인 요청됨, 승인됨, 반려됨, 없음 | "없음"은 빨간 표시. 첫 영업일이 지나면 오늘의 결정에도 올라갑니다 |

**화면 12-2. 월간 계획 만들기** (`/plans/[brandId]/[month]`)

| 영역 | 구성 | 규칙 |
|---|---|---|
| 지난달 요약 | 쓴 광고비, 끝낸 실험, 배운 것 3개 | 성과 리포트(기능 6)와 같은 숫자 |
| 실험 묶음 | 목표, 상품, 시험할 요소 후보. 묶음 추가 | 묶음마다 예상 예산 |
| 총예산 상한 | 입력 칸. 묶음 예상 예산 합계를 기본값으로 | |
| 고객에게 하는 말 | 3줄 이하 자유 입력 | |
| 버튼 | 임시 저장, 고객에게 승인 요청 | 요청 후에는 고칠 수 없고, 고치려면 "요청 취소" |

**화면 12-3. 계획 승인 (고객)** (`/portal/plans/[month]`)

| 구성 | 동작 |
|---|---|
| 지난달 요약, 이번 달 실험 묶음, 총예산 상한, 담당자의 말 | |
| 안내: "승인하시면 이 상한 안에서 담당자가 광고를 올려요. 광고비는 Meta에 등록하신 카드로 나가요." | |
| 버튼: 승인 / 반려 (이유) | 승인 기록은 고칠 수 없습니다 |
| 승인 뒤 | 상한 줄이기는 바로 할 수 있습니다. 늘리기는 담당자가 다시 요청합니다 |

## 기능 13. 추가 자동 멈춤

- **목적:** 사람이 일하지 않는 밤과 주말에 광고비가 새지 않게 합니다.
- **쓰는 사람:** 시스템이 멈추고, 담당 직원과 팀장이 처리합니다
- **관련 문서:** 정책서 12.1, 17절 · 운영 문서 6절 · 시나리오 TS-15
- **지금 코드:** Meta 오류로 멈추는 것은 있습니다 (`TournamentAdvanceService`의 `lastError`). 광고비 검사는 없습니다. 성과 수집은 `TournamentPoller.java` (6시간)

**새 화면은 없고, 기존 화면에 아래를 더합니다.**

| 화면 | 더할 것 |
|---|---|
| 실험 상세 (3-1) | 멈춤 띠: "광고비가 하루 예산의 2배를 넘어 멈췄어요. 원인을 확인한 뒤 다시 시작해 주세요." [다시 시작] / "이번 달 예산 상한에 닿아 멈췄어요. 고객에게 상한을 늘려 달라고 요청해 주세요." [계획 고치기] |
| 오늘 (5-1) | 1순위 카드로 올라갑니다 |
| 알림 | 앱과 이메일로 담당 직원, 팀장에게 갑니다 |
| 고객 이번 달 (11-1) | 상한 도달이면 "이번 달 예산을 다 썼어요" 한 줄과 담당자 연락 안내 |

- 예산 상한 때문에 멈춘 실험의 "다시 시작"은 고객이 상한을 늘려 승인하기 전까지 눌리지 않습니다.

## 기능 14. 영업과 청구 기록 (고객사)

- **목적:** 별도 CRM 없이 문의부터 재계약, 청구와 입금까지 한 고객사 기록으로 관리합니다.
- **쓰는 사람:** 직원 모두가 영업 기록을 봅니다. 청구 기록은 팀장만 봅니다
- **관련 문서:** 정책서 27절 · 조직 문서 3-1 · 영업 문서 · 회계 문서 2, 7절 · 시나리오 TS-16
- **지금 코드:** 없음

**화면 14-1. 고객사 목록** (`/clients`)

| 구성 | 동작 |
|---|---|
| 상태별 칸: 문의 · 상담 · 제안 · 계약 · 재계약 대기 · 종료 | 카드를 끌어 상태를 바꿉니다. 표 보기도 고를 수 있습니다 |
| 카드: 회사 이름, 업종, 담당, 다음 할 일과 날짜, 문의 경로 | 다음 할 일 날짜가 지나면 빨간 표시 |
| 위: "고객사 추가" | 이름, 연락처, 업종, 문의 경로, 다음 할 일 |
| 팀장에게만: 연체 표시 | 입금 기한이 지난 고객사에 표시 |

**화면 14-2. 고객사 상세** (`/clients/[id]`)

| 탭 | 내용 | 규칙 |
|---|---|---|
| 개요 | 상태, 담당, 업종, 문의 경로, 사례 공개 동의, 다음 할 일, 계약 기간 | 받지 않는 업종이면 "상담"으로 넘길 수 없습니다 |
| 상담 메모 | 시간순 메모, 새 메모 입력 | 메모는 고칠 수 없고, 바로잡을 때는 새 메모를 씁니다 |
| 진단 | "진단용으로 가져오기" (기능 9), 진단서 파일 올리기 | 계약하지 않으면 진단 데이터는 30일 뒤 지웁니다 |
| 계약 | 상품(라이트, 스탠다드), 청구 방식(선불, 후불), 시작일, 종료일, 해지 예정일 | "계약으로 바꾸기"를 누르면 브랜드가 만들어집니다 |
| 청구 (팀장만) | 계약 월마다 청구일, 금액, 할인, 입금 기한, 입금일, 세금계산서 번호. "입금 확인" 버튼 | 해지 예정일을 넣으면 마지막 청구 금액을 계산해 보여 줍니다 (회계 문서 2.2) |

- **관련 문서:** 정책서 28절 · 재무 문서 2절 · 시나리오 TS-17

## 17. 지금 코드에서 크게 바뀌는 것

기능명세를 만들려면 아래 구조부터 바꿔야 합니다. 개발 순서를 정할 때 먼저 봅니다.

| 바뀌는 것 | 지금 | 바뀐 뒤 | 기능 |
|---|---|---|---|
| 데이터 주인 | 로그인한 사람 이메일 (`OwnerScoped.java`) | 워크스페이스와 브랜드 | 10, 11 |
| 광고 계정 | 사람마다 1개 (`MetaConnection.java`) | 브랜드마다 1개, 파트너 공유 계정에서 고름 | 10 |
| 역할 | 세션 값, 거의 검사하지 않음 (`lib/auth.ts`) | 서버가 모든 요청에서 검사, 고객 역할 추가, 브랜드별 담당 | 7, 10, 11 |
| 다음 실험 | 판정 뒤 자동 게재 (`TournamentAdvanceService.autoAdvance`) | 초안만 만들고 승인을 거침 | 3, 7 |
| 판정 조건 | 최소 노출 수 없음 (`engine.ts`, `TourEngine.java`) | 최소 노출 수와 판정 불가 안내 | 3 |
| 배운 것 | 실험에서 그때그때 계산 (`deriveLedger`) | 따로 저장, 초안·확정·보관 상태 | 4 |
| 알림 | 브라우저에만 저장 | 서버에 저장 | 공통 |
